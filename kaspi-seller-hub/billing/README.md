# Подписка и оплата через Kaspi — инструкция по запуску

Тарифы по умолчанию (с 18.11.2026):

- **«Старт»** — 1 магазин, 12 000 ₸ в месяц;
- **«Мульти»** — до 3 магазинов, 20 000 ₸ в месяц;
- каждый следующий магазин — +5 000 ₸ в месяц;
- **14 дней бесплатно** для новых пользователей (до 3 магазинов). Всё это можно поменять в админ-панели без программиста.

## Как это работает

1. Пользователь входит в расширении по email (код приходит на почту) → сразу начинается **пробный период (14 дней)**.
2. Когда нужно платить, он открывает **«Подписка»**, выбирает число магазинов и месяцев, вводит номер Kaspi и жмёт **«Выставить счёт»**. Сумму считает сервер — подделать её нельзя.
3. Вы видите счёт в **админ-панели** (`billing/admin/index.html`) → в приложении **Kaspi Pay** выставляете клиенту удалённый счёт на его номер (или он платит по вашему QR).
4. Деньги пришли → в админ-панели жмёте **«Оплата получена»** → подписка продлевается. Если клиент оплатил во время пробного месяца, оплаченный период начнётся **после** пробного — он ничего не теряет.
5. Когда пробный период или оплата заканчиваются, расширение показывает «Нужна подписка» и перестаёт обновлять данные. Данные магазинов не удаляются.
6. Если магазинов больше, чем оплачено, лишние (последние добавленные) не обновляются, пока их не добавят в подписку.

### Автоматические счета и окно с QR

- **За 5 дней до конца** (настраивается: «Напоминать об оплате за, дней») система сама выставляет **один счёт за все подключённые магазины** на месяц: 45 магазинов = 20 000 + 42 × 5 000 = **230 000 ₸** одним платежом. У клиента всплывает окно с суммой и QR Kaspi (раз в день) и приходит уведомление Chrome с QR.
- **Подключили новый магазин** (кнопка «+ Подключить магазин» в панели или просто открыли его кабинет) → сразу окно оплаты. Сумма — только за оставшиеся дни текущего периода (5 000 ₸ за 30 дней, округление вверх до 100 ₸), чтобы все магазины продлевались в один день одним счётом. Магазин включается **после оплаты**. Если до конца периода ≤ 5 дней, новый магазин просто добавляется в счёт за продление.
- **Не оплатили в срок** → кабинет заблокирован; видно только окно с QR, его нельзя закрыть (можно только выйти из аккаунта). Как только вы нажали «Оплата получена», окно у клиента закрывается само в течение ~15 секунд и всё включается.
- У клиента всегда **один открытый счёт** — одна сумма, один QR.

> «Сразу после оплаты» здесь = сразу после вашего подтверждения. Админ-панель сама проверяет новые счета каждые 30 секунд и показывает уведомление. Полностью автоматическое подтверждение (без вас) требует Kaspi Pay API или посредника — см. ниже.
>
> QR из Kaspi Pay — статический: сумму клиент вводит сам (она крупно показана рядом с QR). QR с уже вписанной суммой Kaspi выдаёт только через API.

## Шаг 1. Создать проект Supabase (≈10 минут)

1. Зарегистрируйтесь на https://supabase.com (бесплатно).
2. **New project** → придумайте имя (например, `seller-hub`) и пароль базы (сохраните его) → регион **West EU (Ireland), eu-west-1** — тот же, что указан в политике конфиденциальности (`legal/privacy.html`); если меняете регион, обновите и политику.
3. Дождитесь, пока проект создастся (1–2 минуты).

## Шаг 2. Создать таблицы

1. Слева **SQL Editor** → **New query**.
2. Откройте файл `billing/supabase/001_billing.sql`, скопируйте **весь** текст, вставьте → **Run**.
3. Должно появиться «Success». Повторный запуск безопасен.

### Шаг 2а. Сотрудники (сборщики)

После `001_billing.sql` выполните в том же SQL Editor `002_team.sql`. Файл можно запускать
повторно.

Он создаёт команду владельца: приглашения сборщиков по почте, их права (магазины, «Принять»),
отключение в один клик. Данных о заказах на сервере нет. Сервер знает только, кто на кого

- **вопросы в поддержку** из расширения с техническим отчётом;
- **счётчики запросов к API** — только числа, без заказов и токенов;
- **ключ для уведомлений в Telegram**.

### Шаг 2в. Пульт (аналитика продукта)

Затем выполните `004_insights.sql`. Его тоже можно запускать повторно. Он добавляет вкладку «Пульт» в админке.

### Шаг 2г. Тарифы, удержание и Telegram-бот

Затем выполните `005_growth.sql`. Его тоже можно запускать повторно.

### Шаг 2д. Индексы

Выполните `006_indexes.sql`. Его тоже можно запускать повторно.

Затем `007_bot_batch.sql` (бот отправляет порциями, без повторов при обрыве). Можно запускать повторно.

Затем `008_bot_lock.sql` (одновременно работает только один запуск бота, без дублей сообщений; зависшая блокировка снимается сама через несколько минут). Можно запускать повторно.

В нём же функция `health()` для внешнего мониторинга доступности: `POST /rest/v1/rpc/health` с anon-ключом возвращает `{"ok": true}`.

Далее по порядку все файлы `009_…` → `027_…`, затем `grants.sql` последним. Все можно запускать повторно.

### Шаг 2е. Телеметрия интерфейса пачками (`027_ux_events_batch.sql`)

Раньше расширение отправляло отдельный запрос на каждое событие интерфейса: до 250 запросов в минуту от активного пользователя. С `027` вся пачка уходит одним запросом (`track_ux_events`).

**Выполните `027_ux_events_batch.sql` и `grants.sql` ДО выпуска новой версии расширения.** Если новая версия попадёт на сервер без этой функции, ничего не сломается, но данные для вкладки UX в «Пульте» перестанут записываться. Старые версии расширения продолжат работать через прежнюю `track_ux_event`.

### Резервные копии

Workflow `seller-hub-db-backup` каждую ночь делает зашифрованный дамп БД и хранит его 30 дней в артефактах GitHub Actions. Нужны секреты `SUPABASE_DB_URL` (строка подключения из Project Settings → Database) и `BACKUP_PASSPHRASE` (храните копию вне GitHub). Восстановление описано в начале файла workflow.

## Шаг 3. Вход по коду из письма

1. **Authentication → Sign In / Providers → Email**: должно быть включено.
2. **Authentication → Emails (Email Templates)**: в шаблонах **Magic Link** и **Confirm signup** замените текст на:

   ```
   <h2>Код для входа в SaudaPulse</h2>
   <p>Ваш код: <b style="font-size:22px">{{ .Token }}</b></p>
   <p>Если вы не запрашивали код — просто проигнорируйте письмо.</p>
   ```

3. ⚠️ Встроенная почта Supabase отправляет **всего несколько писем в час** — этого хватает для проверки, но не для клиентов. Перед запуском подключите свою почту: **Authentication → Emails → SMTP Settings** (подойдут Resend, Mailgun, Яндекс 360 или почта вашего домена).

### Шаг 3а. Капча «не робот» перед письмом с кодом (Cloudflare Turnstile)

Без капчи бот может запросить тысячи кодов на чужие адреса: лимит писем закончится, настоящие клиенты не смогут войти.

Как устроено: правила Chrome запрещают загружать скрипт Cloudflare прямо в расширение. Поэтому капча живёт на сайте (`https://saudapulse.kz/captcha`), а расширение и админ-панель показывают её в маленьком окне и получают от неё одноразовый токен. Токен уходит в Supabase вместе с запросом кода, и Supabase сам проверяет его у Cloudflare.

**Порядок важен.** Если включить капчу в Supabase раньше, чем клиенты обновятся, старые версии расширения не смогут получить код.

1. **Cloudflare → Turnstile → Add widget.** Имя: SaudaPulse, домен (hostname): `saudapulse.kz`, режим **Managed**. Сервис бесплатный. Получите **Site Key** (публичный) и **Secret Key** (секретный).
2. **Страница на сайте.** Возьмите `billing/captcha/index.html`, замените `SITE_KEY` на ваш Site Key и опубликуйте по адресу `https://saudapulse.kz/captcha`. Сайту нельзя запрещать показ этой страницы во фрейме (`X-Frame-Options` / `frame-ancestors`).
3. **Проверка.** Откройте `https://saudapulse.kz/captcha` в браузере: должна появиться галочка Cloudflare.
4. **Выпустите версию расширения** с капчей. Адрес уже прописан в `shared/billing-config.js` → `CAPTCHA.pageUrl`. Пока капча в Supabase выключена, всё работает как раньше, просто перед письмом мелькает проверка.
5. **Подождите, пока большинство клиентов обновится** (Chrome обновляет расширения сам, обычно за 1–3 дня). Затем: **Supabase → Authentication → Attack Protection → Enable Captcha protection → Cloudflare Turnstile**, вставьте **Secret Key**, сохраните.
6. **Проверьте вход** в расширении и в админ-панели на чистом профиле Chrome.

Если страница капчи недоступна (сайт упал, ещё не опубликована), расширение через 6 секунд запрашивает код без токена. Пока капча в Supabase выключена, вход работает. После включения клиент увидит сообщение «проверка "не робот" не пройдена», и никто не застрянет молча.

Уже вошедших клиентов капча не касается: сессия продлевается без неё. Она нужна только при запросе нового кода.

## Шаг 4. Подключить расширение к Supabase

1. **Project Settings → API**: скопируйте **Project URL** и ключ **anon public**.
2. Откройте файл `shared/billing-config.js` и вставьте их:

   ```js
   supabaseUrl: 'https://xxxx.supabase.co',
   supabaseAnonKey: 'eyJhbGciOi…',
   ```

3. На `chrome://extensions` нажмите ↻ у расширения.
   Ключ **anon** публичный по замыслу — доступ защищён правилами в базе. **Никогда** не вставляйте ключ `service_role`.

> Пока эти два поля пустые, расширение работает в **режиме разработчика**: без входа и без ограничений. Перед раздачей клиентам их нужно заполнить.

## Шаг 5. Сделать себя администратором

2. **SQL Editor** → выполните (подставьте свой email):

1. Откройте в Chrome файл `billing/admin/index.html` (двойной клик).
2. Первый раз вставьте те же **Project URL** и **anon key** → «Сохранить».
3. Войдите по коду из письма.
4. Вкладка **«Цены и QR»**:

   - **Инструкция для клиента** — что увидит клиент рядом с суммой.
   - Цены и пробный период — тут же.

## Шаг 7. Подписанная лицензия (защита от взлома) — обязательно перед продажей

Без этого шага срок подписки можно «продлить», поправив данные браузера в DevTools. С ним срок подписки подписывает Supabase своим секретным ключом, а расширение проверяет подпись открытым ключом: подделать её нельзя.

1. **Project Settings → JWT Keys**: включите асимметричные ключи (ECC P-256 / ES256). Если там ещё «Legacy JWT secret» — создайте новый ключ ES256 и сделайте его текущим (Rotate). Сессии клиентов перейдут на новый ключ при следующем обновлении токена (в течение часа).
2. **Authentication → Hooks → Custom Access Token** → включите, тип **Postgres**, схема `public`, функция **`custom_access_token_hook`** → Save. (Функцию создал файл `001_billing.sql` — выполните его заново, если запускали раньше.)
3. Откройте в браузере `https://ВАШ-ПРОЕКТ.supabase.co/auth/v1/.well-known/jwks.json` — там список `keys`. Скопируйте объект(ы) ключа целиком в `shared/billing-config.js`:

   ```js
   licenseKeys: [{ "kty": "EC", "crv": "P-256", "x": "…", "y": "…", "kid": "…", "alg": "ES256" }],
   ```

   Это **открытый** ключ, его можно публиковать. Если позже будете менять ключ (Rotate), добавьте новый ключ в этот список **до** ротации и выпустите обновление расширения.
4. Проверка: войдите в расширении — в «Подписке» должен быть обычный статус. Если видите «Подписка не подтверждена» — хук или ключ не настроены.

Названия пунктов меню Supabase иногда меняются — если не нашли, ищите в документации Supabase «asymmetric JWT signing keys» и «Custom Access Token Hook».

### Схема подключения (`shared/billing-config.js`)

| Поле | Откуда взять | Что проверяет расширение |
|---|---|---|
| `supabaseUrl` | Project Settings → API → Project URL (`https://xxxx.supabase.co`) | Адрес сервера; из него же строится ожидаемый `iss` токена: `<supabaseUrl>/auth/v1` |
| `supabaseAnonKey` | Project Settings → API → `anon public` | Публичный ключ запросов; сборка откажется, если вставлен `service_role` / `sb_secret_` |
| `licenseKeys` | `https://xxxx.supabase.co/auth/v1/.well-known/jwks.json` → массив `keys` | Подпись токена: только `ES256` (P-256) или `RS256`, `aud = authenticated`, свой `sub`, есть `exp`/`iat` |

```
Supabase Auth ──(приватный ключ ES256 + custom_access_token_hook → claim ksh)──► access_token
      │                                                                              │
      └── jwks.json (открытый ключ) ──► licenseKeys в расширении ──► verifiedClaims() ┘
                                                                         │
                         licenseView(): срок/лимиты берутся ТОЛЬКО из ksh ──► licenseGate (service-worker.js)
```

- Пустые `supabaseUrl`/`supabaseAnonKey` → режим разработчика (всё бесплатно). Пустой `licenseKeys` → срок читается из данных браузера и правится через DevTools. `tools/build-release.mjs` не соберёт релиз ни в одном из этих случаев.
- `licenseKeys` заморожен при загрузке: добавить «свой» ключ из консоли воркера нельзя. Если в объект ключа случайно попал приватный параметр `d` — ключ игнорируется (и его срочно нужно ротировать).
- Проверка: `node tests/unit/license-signature.test.mjs` (подделка срока, чужой ключ, `alg: none`, HS256, правка кэша в DevTools).

## Шаг 8. Релизная сборка для Chrome Web Store

```bash
node tools/build-release.mjs
```

Получится `dist/kaspi-seller-hub-<версия>.zip` — его и загружайте в Chrome Web Store. Скрипт **откажется** собирать, если: не заполнены адрес и ключ Supabase (иначе расширение работало бы бесплатно), нет ключа подписи, вставлен секретный ключ `service_role`, остались тестовые адреса. В сборку не попадают демо-страницы, админ-панель и SQL; расширению разрешено обращаться только к kaspi.kz и вашему Supabase.

Раздавайте расширение **только через Chrome Web Store**: Chrome проверяет файлы установленного из магазина расширения и отключает копию, в которой изменён код.

## Защита от взлома — что сделано и где предел

| Попытка | Что происходит |
|---|---|
| Поправить срок подписки в данных браузера (DevTools) | Игнорируется: срок берётся только из подписанного токена |
| Подделать или переподписать токен, «alg: none» | Подпись не сходится → «Подписка не подтверждена» |
| Отключить интернет, чтобы старая оплата «жила вечно» | Работает максимум 3 дня после последней проверки (`offlineGraceDays`) |
| Перевести часы компьютера назад | Блокировка «Неверное время на компьютере» |
| Новая почта ради ещё одного бесплатного периода | Пробный период привязан к магазину Kaspi: на уже использованном магазине его нет |
| Изменить цену, отметить счёт оплаченным, стать админом через API | Запрещено базой (проверено тестами на атаки) |
| Засыпать базу счетами/запросами | Не больше 30 счетов в сутки на клиента; согласия не дублируются |
| Вставить свой счёт с суммой 1 ₸ | Сумму считает только сервер |

**Честный предел.** Расширение работает на компьютере клиента, а заказы берёт напрямую у Kaspi. Человек, который распакует расширение, перепишет его код и установит в режиме разработчика, может выключить проверку подписки — так устроено любое ПО без своего сервера с данными. Наша защита делает это заметно сложнее, чем заплатить 20 000 ₸: нужна переделка кода, режим разработчика Chrome (с постоянным предупреждением) и ручная установка, а обновления из магазина такая копия получать не будет. Если когда-нибудь понадобится защита и от этого — часть работы (например, синхронизацию заказов) нужно перенести на ваш сервер; это отдельный большой этап.

## Выгрузка товаров и прайс-листы

Повторный запуск `001_billing.sql` создаёт хранилище **pricelists** (Storage) и правила доступа — больше ничего настраивать не нужно.

- Клиент в разделе **«Выгрузка товаров»** заводит товары и выбирает, в какие магазины их выложить: во **все** или в **отмеченные**.
- **Карточка нового товара** уходит в Kaspi по официальному API — отдельно в каждый выбранный магазин его токеном. Kaspi проверяет карточку; статус виден в таблице.
- **Цена и наличие** идут через прайс-лист. Расширение само собирает XML для каждого магазина и кладёт его в Storage по секретной ссылке; клиент один раз вставляет ссылку в кабинете Kaspi (Товары → Загрузить прайс-лист → Автоматическая загрузка). Kaspi забирает изменения раз в час.
- ⚠️ Kaspi снимает с продажи товары, которых **нет** в прайс-листе. Поэтому прайс-лист магазина включается только после того, как клиент загрузил текущий ассортимент (Excel/XML из кабинета) и поставил галочку подтверждения.
- Писать в прайс-лист может только его владелец и только с активной подпиской; магазинов — не больше, чем оплачено. После окончания подписки последний файл остаётся (Kaspi продолжает его читать), но обновления не принимаются.

## Тарифы при подключении других маркетплейсов (решение от 17.11.2026)

Пока работает только Kaspi: 20 000 ₸ в месяц за пакет до 3 магазинов, +5 000 ₸ за каждый следующий
(`billing_config`: `base_price`, `base_stores`, `extra_store_price`).

Когда будут подключены Ozon и Wildberries, сумма складывается по площадкам:

| Площадка | Первый магазин (или пакет) | Каждый следующий |
|---|---|---|
| Kaspi | 20 000 ₸ за пакет до 3 магазинов | +5 000 ₸ |
| Ozon | 10 000 ₸ | +8 000 ₸ |
| Wildberries | 10 000 ₸ | +8 000 ₸ |

Примеры:
- Kaspi 3 + Ozon 1 + WB 1 = 40 000 ₸;
- Kaspi 5 + Ozon 2 + WB 2 = 66 000 ₸.

**Ozon и Wildberries можно купить без Kaspi**: например, только WB с 1 магазином = 10 000 ₸.
**Скидки за пакет «все площадки» нет**: цена всегда равна сумме по площадкам.

Для этого `billing_price` должна считать по площадкам: в счёте и лицензии вместо одного числа
магазинов будет число магазинов на каждой площадке.

## Ежедневная работа

1. Вкладка **«Ждут оплаты»** — новые счета: email, номер Kaspi, сумма.
2. В приложении **Kaspi Pay** → удалённая оплата / выставить счёт → номер клиента и сумма.
3. Деньги пришли → **«Оплата получена»** (можно записать номер операции Kaspi).
4. Вкладка **«Клиенты»** — кто на пробном, кто оплатил, у кого закончилось; кнопка **«+ дни»** — подарить дни (компенсация, акция).

### Вопросы клиентов — вкладка «Вопросы»

Клиент пишет из раздела расширения «Помощь» → «Написать в поддержку». К вопросу сам прикладывается
технический отчёт: версия, браузер, число магазинов, последние ошибки. Токенов и данных покупателей
в нём нет. Поэтому не нужно выспрашивать, «какая у вас версия» и «что за ошибка».

1. Откройте вопрос и прочитайте его. Если нужно, разверните «Технический отчёт».
2. Выберите **«Шаблон…»**: готовые ответы про токен, принтер, оплату и сбой Kaspi. Поправьте текст,
   если нужно, и нажмите **«Ответить»**.
3. Клиент увидит ответ в расширении в течение 15 минут. Он также получит уведомление Chrome, значок
   у «Помощь» и пункт «Поддержка ответила» на главной.

Свой ответ можно сохранить кнопкой **«Сохранить как шаблон»**. Шаблоны хранятся в этом браузере.
Клиент может отправить не больше 5 вопросов в час.

### Сбой у Kaspi — вкладка «Состояние»

- **«API маркетплейсов за последний час»** показывает, сколько клиентов работает и у скольких ошибки,
  и почему: ошибка сервера, нет связи, неожиданный ответ.
  - «Сбой» — это когда ошибки сразу у многих клиентов. По умолчанию: от 3 человек и от 30 % клиентов.
  - Неверный токен одного клиента сбоем не считается.
- **«Сообщение для всех клиентов»**: напишите одно сообщение и выберите, сколько его показывать
  (3 часа, 12 часов, сутки).
  - Через 5 минут его увидят все клиенты, даже те, кто ещё не вошёл в аккаунт.
  - Так вместо 200 одинаковых вопросов вы пишете одно сообщение.

## Пульт — где клиенты застревают и почему уходят

Первая вкладка админки. Период выбирается сверху: 7, 30, 90 дней или год.

- **Плитки:**
  - активные за неделю;
  - новые клиенты;
  - доля перешедших с пробного периода на оплату;
  - **NPS**;
  - доля ответов поддержки, которые помогли.
- **Кому написать первым.** Клиенты, которые застряли или вот-вот уйдут, с кнопкой «Написать»:
  - поставили 0–6;
  - пробный период кончается, а магазин не подключён;
  - не подключили магазин за 2 дня;
  - не заходят 7 дней и больше;
  - не настроили печать;
  - подписка недавно закончилась.
- **Воронка.** Сколько новых клиентов дошли до каждого шага:
  - шаги: магазин, заказы, печать, себестоимость, копия, оплата;
  - «узкое место» — шаг, на котором теряется больше всего людей;
  - справа — сколько обычно проходит от регистрации до шага.
- **Чем пользуются.** Разделы и действия: сколько продавцов и сколько раз. Отметка «никто не
  пользуется» подсказывает, что можно упростить или убрать.
- **Кто остаётся.** Клиенты по неделям регистрации и доля активных через 1–5 недель. Если после
  изменения в продукте цифры растут, изменение работает.
- **NPS.** Вопрос «Насколько вероятно, что порекомендуете?» по шкале 0–10.
  - Задаётся через 14 дней работы, затем раз в 90 дней. Это карточка на главной, а не всплывающее
    окно.
  - NPS = % ответивших 9–10 минус % ответивших 0–6. Выше 0 — хорошо, выше +30 — отлично.
  - Комментарии показаны с почтой клиента.
- **Почему не продлевают.** Причины и комментарии из опроса при окончании пробного периода или
  подписки. Опрос встроен в окно оплаты.

Что присылает расширение: каждые 15 минут, только числа (по разделам и действиям за день, какие
из пяти шагов сделаны). Заказов, товаров, сумм и токенов в этих данных нет. Пункт об этом есть в
политике конфиденциальности.

> Пока клиентов меньше 100, относитесь к процентам как к подсказке, кому позвонить, а не как к
> статистике.

## Тарифы и удержание — как это работает

- **«Старт» → «Мульти».** Продавец на «Старт» нажимает «+ Добавить магазин» и видит окно с выбором
  (не запрет):
  - «Добавьте ещё 2 магазина за +8 000 ₸/мес»;
  - сумма к оплате сейчас — только за оставшиеся дни: (20 000 − 12 000) / 30 × дни;
  - кнопка «Попробовать 3 магазина бесплатно 24 часа» — один раз на аккаунт;
  - кнопка «Расширить тариф сейчас» — сразу окно оплаты.
- **После оплаты.** Вы нажимаете «Оплата получена» → в течение ~15 секунд у клиента открываются
  3 магазина.
- **Льготный период.** Оплаченный срок кончился, продление не оплачено → ещё 4 дня (настраивается в
  «Цены и QR») всё работает, вверху плашка «оплатите продление», в Telegram — напоминание раз в день.
  Пробный период льготы не даёт. Отменённая подписка — тоже.
- **«Отменить подписку»** (раздел «Подписка»):
  - сначала причина;
  - «Дорого» → скидка 30 % на 2 следующих счёта или переход на «Старт»;
  - «Закрыл магазин» → бесплатная заморозка на 30 дней: оплаченные дни переносятся, разморозить
    можно раньше;
  - «Не хватает функций» → текст приходит вам вопросом во вкладку «Вопросы».

  Каждое предложение — не чаще раза в полгода. «Всё равно отменить» всегда в один клик: доступ до
  конца срока, без продления и напоминаний. Причины видны в «Пульт» → «Почему не продлевают».
- **Возврат клиентов (win-back)**, через Telegram, если клиент его подключил:
  - через 30 дней после окончания — «что нового» (текст пишете вы в «Состояние»);
  - через 60 дней — скидка 50 % на первый месяц, действует 30 дней и сразу учитывается в счёте.

> Электронной почты для таких писем у сервиса пока нет (письма Supabase — только коды входа). Тем, у
> кого нет Telegram, пишите сами из «Пульт» → «Кому написать первым».

## Telegram-бот для продавцов (20 минут настройки)

Что получает продавец:

- в 09:00 по Алматы — сводку за вчера: заказы и сумма, отправлено, заказы под угрозой просрочки;
- сразу — «🚨 Заказ №… под угрозой просрочки»;
- если 6 дней не заходил — «всё в порядке? мы на связи»;
- напоминания льготного периода и win-back.

Под каждым сообщением кнопки «📦 Посмотреть заказы» и «💬 Поддержка».

**Откуда берутся данные.** Цифры для сводки и срочные сообщения отправляет расширение, пока у
продавца открыт Chrome; токены Kaspi на сервер не попадают. Если Chrome был закрыт до полуночи, в
сводке написано «по данным на ЧЧ:ММ».

**Как настроить:**

1. В **@BotFather** → `/newbot` → получите токен бота и его имя (например, `SellerHubBot`).
2. В админке → «Состояние» → «Telegram-бот для продавцов»:
   - впишите имя бота;
   - ссылку на сайт — кнопка «Посмотреть заказы» ведёт на `/open`;
   - ссылку на поддержку;
   - нажмите **«Создать ключ бота»** и скопируйте ключ.
3. Разверните функцию (нужен [Supabase CLI](https://supabase.com/docs/guides/cli)):

   ```bash
   supabase secrets set BOT_TOKEN=<токен от BotFather> BOT_KEY=<ключ из админки> WEBHOOK_SECRET=<любая длинная случайная строка>
   ```

   ```bash
   supabase functions deploy telegram-bot --no-verify-jwt
   ```
4. Скажите Telegram, куда слать сообщения боту (один раз):

   ```bash
   curl "https://api.telegram.org/bot<ТОКЕН>/setWebhook?url=https://<проект>.supabase.co/functions/v1/telegram-bot/webhook&secret_token=<WEBHOOK_SECRET>&allowed_updates=%5B%22message%22,%22my_chat_member%22%5D"
   ```
5. Утренний запуск: на GitHub → Settings → Secrets добавьте `BOT_KEY` (и `SUPABASE_URL`, если ещё
   нет). Задача `seller-hub-bot` будет вызывать функцию каждый день в 09:00 по Алматы. Проверить
   сразу: Actions → seller-hub-bot → Run workflow.

**Безопасность:**

- Бот работает только через функции `bot_*` со своим ключом; ключ `service_role` не нужен и не
  используется.
- Ссылка привязки одноразовая, живёт 15 минут.
- Если продавец заблокировал бота, Telegram отвечает 403 — бот это записывает и больше туда не пишет.

## Уведомления в Telegram (10 минут настройки)

Каждые 10 минут задача GitHub Actions `seller-hub-ops-alert` (файл `tools/ops-alert.mjs`) спрашивает
сервер и присылает вам в Telegram одно сообщение, если есть что сказать:

- 🔴 сбой Kaspi или другого маркетплейса у многих клиентов. Пока сбой продолжается, напоминание
  приходит раз в 2 часа. 🟢 приходит, когда всё восстановилось;
- 💬 новые вопросы в поддержку;
- 🧾 новые счета, которые ждут подтверждения, и их сумма.

Данных клиентов в сообщениях нет: только числа.

1. В Telegram напишите **@BotFather** → `/newbot` → получите **токен бота**.
2. Напишите своему боту любое сообщение. Затем откройте в браузере
   `https://api.telegram.org/bot<ТОКЕН>/getUpdates` и найдите `"chat":{"id":…}` — это **chat id**.
3. В админ-панели: «Состояние» → **«Создать ключ»**. Ключ показывается один раз, скопируйте его.
   На сервере хранится только его хеш. Новый ключ отменяет старый.
4. На GitHub откройте репозиторий → **Settings → Secrets and variables → Actions → New repository secret**
   и добавьте пять секретов:
   - `SUPABASE_URL` и `SUPABASE_ANON_KEY` — те же, что в расширении;
   - `OPS_KEY` — ключ из шага 3;
   - `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.
5. Откройте **Actions → seller-hub-ops-alert → Run workflow**, чтобы проверить. Если сообщать нечего,
   в журнале будет «nothing to report».

> Ключ `service_role` для этого не нужен и не используется. Ключ задачи открывает только счётчики.
>
> GitHub может запускать задачу по расписанию с опозданием на несколько минут. Для уведомлений этого
> достаточно.

## Оферта, политика и галочка согласия

- На экране входа под полем email стоит галочка мелким шрифтом: «Я принимаю условия **Публичной оферты** и даю согласие на обработку персональных данных в соответствии с **Политикой конфиденциальности**…». Пока она не отмечена, кнопка «Получить код» не нажимается.
- После входа сервер записывает **дату, версию условий, IP и браузер** (таблица `consents` — журнал, клиент не может его изменить). Видно в админ-панели → «Клиенты» → «Согласие с офертой».
- Тексты лежат внутри расширения: `legal/terms.html` (оферта — `#offer`, политика — `#privacy`). **Заполните в нём всё в [квадратных скобках].** Когда опубликуете тексты на своём сайте, впишите ссылки в `shared/billing-config.js` → `LEGAL.offerUrl` / `LEGAL.privacyUrl` — галочка будет вести туда.
- **Изменили тексты?** Админ-панель → «Цены и QR» → «Версия условий» → поставьте новую (например, сегодняшнюю дату). Каждый клиент при следующем открытии увидит окно «Условия сервиса обновились» и снова поставит галочку; пока не поставит, расширение не работает и счёт выставить нельзя.
- Сервер не даст выставить счёт без принятой оферты (`terms_required`).

## Перед тем как брать деньги

- **Публичная оферта и политика конфиденциальности** — заполните реквизиты в `legal/terms.html` и проверьте у юриста (см. раздел выше).
- **Фискальные чеки (ОФД/онлайн-касса)** за услуги — уточните у бухгалтера, как это делается в вашем случае с Kaspi Pay.
- Автоматическое подтверждение оплаты (без ручного шага) возможно позже через Kaspi Pay API или посредника — база уже готова: нужно будет только вызвать `admin_confirm_invoice` из обработчика платежа.

## Безопасность (что уже сделано)

- Каждый видит только свои данные (Row Level Security); прямые изменения таблиц запрещены.
- Сумму счёта считает сервер; клиент не может продлить себе подписку или стать администратором.
- Действия администратора проверяются в базе (`public.is_admin()`), а не только на странице.
- Проверено на PostgreSQL 16: 98 сценариев (включая согласие с офертой и попытки взлома), включая попытки подделки (`billing/` → см. отчёт в истории разработки).

## Примечание к Supabase advisors

- «RLS enabled, no policy» на служебных таблицах сделано намеренно: прямой доступ через PostgREST закрыт для всех, данные читаются и пишутся только через RPC с `security definer`. Политики добавлять не нужно.
- `bot_*`, `bot_key_ok`, `ops_digest` доступны только `service_role` (миграция 017). `get_service_status()` публична намеренно: её читают расширение и админка для баннера состояния.
