# Нагрузочный тест сервера подписок

Проверяет SQL-функции подписки под нагрузкой на базе с **50 000 клиентов** (300 000 счетов, 150 000 магазинов).
Заказы Kaspi через этот сервер не идут: каждый пользователь загружает их из Kaspi сам, своим токеном.
Поэтому общий для всех ресурс — только Supabase (вход, подписка, счета).

> Запускайте **только на локальной/тестовой базе**. `seed.sql` создаёт тысячи фиктивных клиентов.

## Как повторить

```bash
createdb loadt
psql -d loadt -f stub.sql            # только для локального PostgreSQL: имитация схемы auth Supabase
psql -d loadt -f ../supabase/001_billing.sql
psql -d loadt -f seed.sql
pgbench -n -c 50 -j 4 -T 30 -f get_license.sql@84 -f hook.sql@14 -f renewal.sql@2 loadt
```

Смесь `84 / 14 / 2` — это реальная доля запросов одного пользователя: проверка подписки, выдача токена (раз в час), счёт на продление.

## Результаты (16.11.2026, PostgreSQL 16, 4 ядра, 128 МБ shared_buffers)

| Что | Результат |
|---|---|
| Проверка подписки до индекса `invoices_user_created` | ~220 запросов/с, 37 мс |
| После индекса | ~4 400 запросов/с, 2 мс |
| Смешанная нагрузка, предел | ~4 700 запросов/с |
| 2 000 запросов/с стабильно | средняя задержка 2,7 мс, 0 ошибок, 0 запросов дольше 100 мс |
| Выдача токена (хук лицензии) | ~32 000/с |
| Админ-панель: «Ждут оплаты» / «Клиенты» (страница 100 строк) | 52 мс / 64 мс |

Нагрузка от одного пользователя (замер настоящего расширения против тестового Supabase):

| Режим | Запросов к серверу в час |
|---|---|
| Обычная работа (панель открыта) | ~7: проверка подписки раз в 10 мин + новый токен раз в час (за 3 мин замера — 0) |
| Последние 5 дней перед продлением | ~7 (счёт на продление пересоздаётся только при изменениях; до исправления было 520/ч) |
| Открыто окно оплаты, вкладка на экране | 240 (проверка «оплачено ли?» каждые 15 с) |
| Окно оплаты, вкладка в фоне | 0 (проверка сразу при возврате на вкладку) |

## Сколько пользователей выдержит

Запас считаем от **300 запросов/с** — это примерно 1/15 от измеренного предела, с поправкой на
более слабый сервер Supabase (2 общих ядра у младших тарифов) и слой API.

| Сценарий | Средняя нагрузка на пользователя | Одновременно онлайн |
|---|---|---|
| Обычный день | 7 запросов/ч | ~150 000 |
| Плохой день: у 10 % открыто окно оплаты | ~30 запросов/ч | ~36 000 |
| Почти невозможный: у всех сразу окно оплаты | 240 запросов/ч | ~4 500 |

Раньше упрёмся не в базу, а в:
1. **Ручное подтверждение оплат.** Каждый клиент платит раз в месяц: 3 000 клиентов ≈ 100 подтверждений в день. Дальше нужна автоматическая проверка оплаты (Kaspi Pay API или посредник).
2. **Письма с кодом входа.** Нужна своя почта (SMTP) и поднятый лимит писем в Supabase → Authentication → Rate Limits.
3. **Тариф Supabase.** Бесплатный проект засыпает после недели без активности — для работы нужен платный. Объём данных маленький: 50 000 клиентов ≈ 110 МБ.
