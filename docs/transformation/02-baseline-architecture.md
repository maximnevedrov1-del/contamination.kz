## 2. Проверенная архитектура

```
Браузер продавца (Chrome MV3)                          Supabase (Postgres + Auth + Storage)
┌────────────────────────────────────────┐             ┌──────────────────────────────────┐
│ dashboard / popup  ──ui:* сообщения──► service-worker│             │ accounts, invoices, team_members │
│ content + network-tap (kaspi.kz, mc.*) │  ──RPC────► │ RPC SECURITY DEFINER (auth.uid())│
│ background/kaspi-api.js ──HTTPS──► Kaspi Shop API    │             │ custom_access_token_hook → JWT   │
│ chrome.storage / IDB: заказы, токены   │             │ price_feeds + бакет pricelists   │
└────────────────────────────────────────┘             └──────────────────────────────────┘
Телефон (PWA, kh/app) ── kaspi-relay (Edge/CF Worker, JWT ES256) ──► kaspi.kz/shop/api
Платёж ──► payment-webhook (HMAC) ──► payment_received() ──► confirm_invoice_core()
Админ (kh/billing/admin) ──► admin_* RPC (is_admin())
```

Факты **[прочитано]**:

- **Заказы не хранятся на сервере.** Таблиц заказов в миграциях нет. Заказы, токены Kaspi, журнал сборки живут в `chrome.storage` / IndexedDB пользователя (`kh/shared/storage.js`, токены шифруются AES-GCM с неизвлекаемым ключом, `token-crypto.js`). Сервер знает только аккаунт, счета, команду и фиды прайс-листов.
- **Три клиента одного бэкенда:** расширение, PWA на телефоне, админка. Телефонное приложение ходит к Kaspi только через `kaspi-relay`.
- **Обновление лицензии:** клиент вызывает `get_license`, кэширует ответ; при недоступности сервера использует кэш до `offlineGraceDays`. Кэш «из будущего» отбрасывается (`billing.js`, `getLicense`).
- **Режим разработчика:** при пустой конфигурации Supabase `licenseView` возвращает `canUse: true` (`billing.js`, `unconfigured`). Релизная сборка отказывается собираться с пустой конфигурацией и без ключей подписи (проверено в CI-шаге и [запущено], раздел 6).

## 4. Изоляция арендаторов (tenant isolation)

**Ключ арендатора:** `auth.users.id`, в таблицах это `accounts.user_id` / `invoices.user_id` / `price_feeds.user_id`; у команды — `team_members.owner_id` (ссылка на `accounts.user_id`). Идентификатор берётся из `auth.uid()` внутри функций, параметром от клиента не принимается (исключение: админские функции с `p_user`, закрытые `is_admin()`). **[прочитано]** в 001, 002, 013, 028.

Механизм, два слоя:
1. **RLS** включён на таблицах 001/002 и далее; прямые политики есть только `accounts_read_own` и `invoices_read_own` (SELECT, `user_id = auth.uid()`). У остальных таблиц политик нет, права на таблицы отозваны (`revoke all ... from anon, authenticated`), доступ только через функции.
2. **SECURITY DEFINER-функции с `set search_path = public`**, проверяющие `auth.uid()` и, где нужно, `has_access()`.

Дополнение от Haiku-discovery (статический разбор 001–034 и `grants.sql`, **[отчёт Haiku, выборочно подтверждён мной]**):
- RLS включён на всех 32 таблицах схемы `public`; политик ровно: `accounts_read_own`, `invoices_read_own`, админская политика `pending_storage_cleanups` и 6 политик `storage.objects` для бакета `pricelists`. У остальных таблиц политик нет и права отозваны, доступ только через RPC.
- Из 77 функций, выданных `authenticated`, каждая привязана к `auth.uid()` либо чистая (`billing_price`); все `admin_*` содержат `is_admin()`. `team_join(p_owner)` и `team_check(p_owner)` принимают идентификатор владельца, но членство сверяют по `auth.uid()` и email.
- `anon` вызывает ровно две функции: `get_service_status()` и `health()`. Ранние анонимные права на бот-функции отозваны в 017 и `grants.sql`.
- Почти все DEFINER-функции закреплены `search_path = public`, и только 12 помощников перезакреплены на `''` (010).

Что я **не** проверял: все 34 миграции построчно (лично читал 001, 002, 013, 028, начало 034, `grants.sql`), и совпадение `grants.sql` с боевой базой (доступа к проекту Supabase нет). Тесты атак в SQL-наборе (29 файлов) зелёные на baseline.

Особенности границы:
- Бакет `pricelists` **публичный** (Kaspi должен читать XML по ссылке). Секрет — случайный `feed_id` (uuid) в пути; запись разрешена только владельцу фида при активной подписке (`can_write_feed`). Утечка ссылки раскрывает только цены и остатки.
- Антизлоупотребление пробным периодом: `store_claims` (SHA-256 от идентификатора магазина Kaspi); второй аккаунт с уже занятым магазином теряет пробный период (`get_license`, 013).

## 5. Жизненный цикл подписки

Действующая схема (миграции 001–033, в продакшене 001–018 и 024, остальное по пакетам `APPLY-PROD-2026-11-24*`):

```
регистрация ─► ensure_account() ─► trial (14 дн., trial_store_limit)
trial/paid ─► create_invoice ─► pending ─► оплата ─► payment_received / admin_confirm_invoice
                                             └► confirm_invoice_core (единственное место «paid»)
статусы get_license: frozen → active (paid_until>now) → trial → grace (grace_days) → expired
expired ⇒ lim = 0 ⇒ расширение: canUse=false, licenseGate → subscriptionRequired
```

- `confirm_invoice_core` блокирует счёт и аккаунт (`for update`), требует `status='pending'`, продлевает от `greatest(now, paid_until, trial_ends_at)`, сбрасывает отмену/понижение, начисляет реферальный бонус +14 дней один раз **[прочитано]**.
- Автоподтверждение: только точная сумма по ожидающему счёту; всё остальное в очередь `review` **[прочитано]**.
- Клиентская сторона: `licenseGate` в service worker блокирует действия из `NEEDS_LICENSE`, а действия из `WRITES` блокирует и пользовательский `readOnly` **[прочитано]**.

**Риск миграции (подтверждён чтением и запуском):** WIP-миграция `034` вводит статус `free` («тариф Бесплатно»), которого в расширении нет: в `background/billing.js`, `shared/*.js`, `dashboard.js`, `app/js/main.js` строки `'free'` не найдены **[прочитано, grep]**. Без доработки клиента `free` будет либо трактоваться как не-`active`, либо потеряет доступ, это решение для Stage 03. Миграции 033 и 034 не входят ни в один пакет `APPLY-PROD`.

## 10. Текущие ограничения: безопасность

1. **Лицензия и PIN проверяются на клиенте.** Расширение — код пользователя; тот, кто изменит его, снимет блокировку действий в браузере. Подпись claims защищает данные лицензии от подделки хранилища, но не отключение `licenseGate`. Серверно защищены только RPC: фиды, команда, счета. Заказы локальны, поэтому серверно «закрыть» их нельзя.
2. **PIN упаковщика/владельца только на клиенте** (`staff.js`), сервер проверяет статус упаковщика раз в 2 минуты.
3. **Нет CSP с `connect-src`** в `site-deploy/_headers`; для `/app/*` есть `frame-ancestors 'none'`.
4. **Реальный платёжный провайдер не подключён**: работает только `generic` (HMAC), `aipay` отвечает 501. Платежи подтверждаются вручную или через общий webhook.
5. Публичный бакет прайс-листов (раздел 4); `http://localhost/*` и `file://` есть в dev-манифесте (в релизе удаляются).
6. Нет сторонних трекеров ошибок; собственная телеметрия. Хорошо для приватности, но слабая наблюдаемость.
7. Ограничения аудита: непросмотренные миграции и функции (раздел 4), `selectors.js`, `content.js`, `network-tap.js` не разобраны.
8. **`grants.sql` не применяется ни в CI, ни в `run.sh`**, поэтому закрытое состояние прав (в продакшене оно задаётся именно им) тестами не проверяется. Заголовок `grants.sql` говорит «001..033», а 034 меняет права (`034:509-513`): рассинхрон документации. По отчёту Haiku, `grants.sql` отзывает права по умолчанию только у `public` и `anon`, у `authenticated` нет, так что новая функция доступна любому вошедшему, пока её явно не закрыли [не проверено на боевой базе].
9. Расширение объявляет `externally_connectable` для `saudapulse.kz` и `*.saudapulse.kz`: все поддомены попадают в доверенную зону [по отчёту Haiku].
10. Четыре пересекающихся снимка `APPLY-PROD-2026-11-24{,-b,-c,-d}.sql` дублируют определения: риск расхождения с миграциями.
11. Секреты CI (имена, значения не читались): `SUPABASE_URL`, `BOT_KEY`, `SUPABASE_DB_URL`, `BACKUP_PASSPHRASE`, `SUPABASE_SERVICE_ROLE_KEY`, `OPS_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Действия закреплены на тегах (`@v4`), а не на SHA. Отслеживаемых файлов с секретами не найдено.
12. Тесты, пропущенные в CI: `bot-greeting`, `bot-support`, `ops-daily` (на baseline зелёные при ручном запуске). Версии Playwright в CI расходятся (1.48.2 и 1.63.0).

## 11. Текущие ограничения: производительность и эксплуатация

Замеров под нагрузкой на этом этапе не делалось (нагрузочные тесты `tests/load`, `tests/perf` не запускались). Известные факты из кода:
- Kaspi API: до 60 запросов одновременно, повторы с задержками, брейкер 3 ошибки → пауза 10 минут (`kaspi-api.js`, `api-breaker.js`).
- Relay: 300 запросов в минуту на пользователя; лимитер хранится в памяти экземпляра (при нескольких экземплярах лимит не общий) **[не проверено]**.
- Кэш счетов: 30 дней, 500 записей, 50 МБ (`INVOICE_LIMITS`); `unlimitedStorage` в манифесте.
- `site-landing/index.html` ~1 МБ в одном файле, собирается вручную (нет отслеживаемого скрипта сборки).
- Полный SQL-набор занимает ~60 с (29 свежих баз); юнит-тесты — секунды.
- Единственная точка отказа биллинга — Supabase; при её недоступности работает офлайн-кэш лицензии (`offlineGraceDays`).
