# Kaspi Seller Hub — финальный отчёт о готовности (2026-11-21)

## 1. Итоговый процент готовности

**Итого: 68%**

Формула (сумма «оценка × вес»):

```
Ядро            76 × 0.20 = 15.20
Биллинг и БД    87 × 0.20 = 17.40
Безопасность    86 × 0.20 = 17.20
Telegram-бот    55 × 0.10 =  5.50
Платежи         35 × 0.15 =  5.25
Тесты и CI      67 × 0.05 =  3.35
Юр./экспл./релиз/админка 43 × 0.10 = 4.30
                         ИТОГО = 68.20 → 68%
```

Динамика: `57% -> 63% -> 65% -> 68%`

Кратко: за последний шаг мы усилили то, что уже было сильным: расширение теперь не «падает» при переполнении хранилища, запросов к серверу стало примерно в 3 раза меньше, база защищена от повторных бесплатных триалов и от дыры в проверке ключа бота. Код и база данных близки к рабочему состоянию. Но продукт пока нельзя выпускать: нет юридических страниц и контактов поддержки, платежи подтверждаются только вручную, Telegram-бот ни разу не запускался по-настоящему, а нагрузку на 2000 клиентов никто не проверял. Именно эти пункты, а не код, теперь держат релиз.

## 3. Разбор по 7 направлениям

### 1. Ядро расширения — 76% (вес 20%)

**Что готово (почему такой процент)**
- `storage.js`: функция `safeSet()` оборачивает каждую запись в `chrome.storage`; при нехватке места (QuotaExceededError / lastError) запись логируется и возвращает `{ok:false, kind}`, а не ломает расширение. Есть `getStorageHealth()`.
- Снимки и счета пишутся одной атомарной записью; при сбое удаления старых данных пропускаются. Исправлена ошибка: отпечатки `snapSeen` обновлялись до неудачной записи.
- 7 прямых записей вне `storage.js` (`billing.js:30`, `usage.js:44,83`, `service-worker.js:214,549`, `growth.js:26`, `dashboard/support-view.js:76`) теперь логируют ошибку, а не бросают её.
- Лимиты Kaspi: MAX_IN_FLIGHT=4, параллелизм 3, retry/Retry-After/429, предохранитель (3 сбоя за 10 минут). Токен шифруется AES-GCM, лицензионные ключи ES256.
- Обновление лицензии: `refreshMinutes` 10 -> 30 плюс случайный разброс ×0.8–1.2 (`background/billing.js:33`, `:294`). Для 2000 клиентов ~67 запросов/мин вместо 200.
- Тест на сбой квоты добавлен (`storage-split` 16 проверок).

**Что осталось до 100%**
- Каталог и себестоимость (`ksh.catalog`, `ksh.costs`) хранятся одним большим ключом — у крупных магазинов это упрётся в лимит.
- Нигде в интерфейсе не показывается состояние хранилища (`getStorageHealth()` никто не выводит): продавец не узнает, что память заканчивается.
- Потребление памяти фоновым процессом (service worker) не измерялось — НЕТ ДАННЫХ.
- Версия 0.1.0, процесса публикации в Chrome Web Store нет (учтено в п. 7).

### 2. Биллинг и база данных — 87% (вес 20%)

**Что готово (почему такой процент)**
- Supabase `kaspi-seller-hub`: 12 миграций применены, в репозитории 12 совпадающих файлов (001…012).
- RLS включён на 21 из 21 таблицы; политики оптимизированы; везде исправлен `search_path`; добавлен индекс на внешний ключ; таблица `admins` есть.
- Миграция 012 (`012_trial_and_rate_hardening`): `store_claims` с `ON DELETE SET NULL` (записи о магазине переживают удаление аккаунта), `get_license` использует `is distinct from`. Итог: один бесплатный триал на магазин, независимо от почты. Ключ магазина на клиенте = `sha256('ksh:'+id.trim().toLowerCase())`.
- 011 исправила `bot_key_ok` (пустой хэш больше не пропускает), `ops_digest` проверяет ключ до `for update`. Обе проверены Opus.
- Реальных клиентов ещё нет (accounts=1, invoices=1, admins=1, store_claims=0, tg_links=0) — значит, боевых сбоев не было, но и боевой проверки тоже.

**Что осталось до 100%**
- Нагрузочного теста на 2000 клиентов не было — НЕТ ДАННЫХ.
- Тариф Supabase и наличие резервного восстановления на любой момент (PITR) неизвестны; восстановление из бэкапа ни разу не проверялось.
- SQL-тесты (`run.sh`) грузят только миграции 001–008, поэтому 009–012 автоматически не проверяются.
- Косметика: имя применённой миграции `001_billing_revoke_fix` не совпадает с файлом 009 в репозитории.
- Хитрый клиент может не присылать ключ магазина; полностью закрывается только проверкой магазина на стороне сервера через Kaspi.

### 3. Безопасность — 86% (вес 20%)

**Что готово (почему такой процент)**
- Аудит Opus: все 8 анонимных функций `SECURITY DEFINER` (`bot_*`, `ops_digest`, `get_service_status`) сначала проверяют ключ; `admin_confirm_invoice`, `create_invoice`, `get_license`, `team_*` проверяют `is_admin()` / `auth.uid()`.
- Миграция 011: закрыта дыра «открыто при пустом хэше» в `bot_key_ok` (`coalesce(...,false)`).
- Токен Kaspi шифруется AES-GCM, лицензии подписаны ES256, RLS везде, пути поиска функций зафиксированы.
- Все 14 функций `admin_*` защищены `is_admin()`.

**Что осталось до 100%**
- Защита от утёкших паролей (Leaked Password Protection) выключена.
- CAPTCHA на регистрации не настроена.
- Обязательность подтверждения почты (Confirm email) — НЕТ ДАННЫХ (неподтверждённых пользователей 0).
- Обход одного триала через изменённый клиент закрывается только серверной проверкой магазина.
- Секреты бота (`BOT_TOKEN`, `BOT_KEY`, `WEBHOOK_SECRET`) — состояние НЕТ ДАННЫХ (см. п. 4).

### 4. Telegram-бот — 55% (вес 10%)

**Что готово (почему такой процент)**
- Edge Function `telegram-bot` развёрнута, ACTIVE v4.
- Блокировка запуска TTL 135 с больше бюджета выполнения 45 с; тест `bot-run` (5 проверок) проходит.
- Функции `bot_*` в базе защищены ключом (011).

**Что осталось до 100%** (нового с прошлого раза нет — оценка не менялась)
- Секреты `BOT_TOKEN`, `BOT_KEY`, `WEBHOOK_SECRET`, `SUPABASE_URL`, `SUPABASE_ANON_KEY` — НЕТ ДАННЫХ, выставлены ли они.
- Бот ни разу не работал по-настоящему: `tg_links=0`.
- Расписание только через GitHub cron; `pg_cron` не установлен — запуск зависит от GitHub.
- Нужен сквозной тест: привязка магазина, получение уведомления.

### 5. Платежи — 35% (вес 15%)

**Что готово (почему такой процент)**
- Ручной цикл работает: счёт создаётся (`create_invoice`), админ подтверждает (`admin_confirm_invoice`), лицензия выдаётся (`get_license`). В базе 1 тестовый счёт.
- Админ-функции защищены `is_admin()`.

**Что осталось до 100%** (нового нет — оценка не менялась)
- Всё подтверждается руками: при 2000 клиентов это 35–70 подтверждений в день.
- Нет автоплатежа и нет импорта банковской выписки для автосверки.
- Нет оферты (`offerUrl` пустой) — без неё принимать деньги юридически рискованно.
- Нет проверки работы цикла на реальных деньгах.

### 6. Тесты и CI — 67% (вес 5%)

**Что готово (почему такой процент)**
- Юнит-тесты все проходят: `storage-split` 16, `robust` 38, `token-crypto` 7, `license-signature` 11, `bot-run` 5, `locales` 1108 ключей.
- CI запускает все 6 и падает при ошибке.
- SQL-тесты: 283 пройдено / 0 упало на локальном Postgres 16.
- Добавлен новый тест на сбой квоты хранилища.

**Что осталось до 100%**
- SQL-тесты не покрывают миграции 009–012 (trial, hardening, advisor fixes).
- Нет сквозных тестов (расширение + Supabase + бот вместе) и нагрузочных.
- Нет тестов админ-панели.

### 7. Юридическое / эксплуатация / релиз / админ-панель — 43% (вес 10%)

**Что готово (почему такой процент)**
- Админ-панель `billing/admin/` (`index.html`, `admin.js`, `admin.css`) готова: сборка не нужна, достаточно один раз ввести Project URL и anon key, вход по коду из почты. Все 14 функций `admin_*` существуют. Можно выложить на Cloudflare Pages (+ Cloudflare Access).
- Есть `legal/terms.html`.
- Сборка `dist/kaspi-seller-hub-0.1.0.zip` обновлена 2026-11-21 13:22 (1.5 МБ, с `safeSet`). `dist/` не в git.
- Подготовлены гайды (админ-панель, отчёты).

**Что осталось до 100%**
- `shared/billing-config.js`: `offerUrl=''`, `privacyUrl=''`, контакты поддержки (`whatsapp`, `telegram`, `email`, `hours`) пустые.
- Страницы политики конфиденциальности нет (есть только `legal/terms.html`).
- Админ-панель не развёрнута.
- Нет процесса публикации в Chrome Web Store; версия 0.1.0.
- Мониторинга и дежурства нет; восстановление из бэкапа не проверялось.
