# Вердикт Opus: готовность Kaspi Seller Hub к запуску на 1 000–2 000 платящих продавцов (21.11.2026)

**Моя оценка: ≈ 60% готовности к продакшену на 1–2 тыс. платящих клиентов.**
**Для закрытой беты на 20–50 клиентов: ≈ 80%.** Остаётся 4 действия, все делаются руками владельца за 1–2 дня.

Источники:
- отчёты `READINESS-FINAL-2026-11-21.md`, `SECURITY-FOLLOWUP-…`, `HARDENING-REPORT-…`, `TRIAL-RATE-REPORT-…`;
- точечная проверка кода: `manifest.json`, `background/billing.js`, `background/service-worker.js`, `billing/README.md`;
- Supabase (`kaspi-seller-hub`, `zraktrilvwrfpcbmkqwi`): статус проекта и тариф организации.

Только чтение: в коде, git и базе ничего не менялось.

**Почему ниже, чем 68%.** Прошлый отчёт в основном измерял, насколько готов и защищён **код**, и там всё честно. Я оцениваю, выдержит ли **весь продукт** 1–2 тыс. платящих клиентов: инфраструктура, деньги, юридическая основа, поддержка. Здесь нашлись две вещи, которых не было ни в одном прошлом отчёте:

Код при этом сильный, и расхождение — не претензия к нему.

## 2. Топ-7: чего не хватает (от самого критичного)

### 2.1. Юридическая основа приёма денег (P0)
- **Суть:** в `shared/billing-config.js` пустые `offerUrl`, `privacyUrl` и все `SUPPORT.*`. В репозитории есть только `legal/terms.html`, политики конфиденциальности нет.
- **Чем грозит:** без публичной оферты с реквизитами ИП/ТОО брать оплату с продавцов нельзя. Без политики конфиденциальности Chrome Web Store отклонит расширение, которое работает с токенами и данными заказов. Клиенту некуда писать: каждый вопрос превращается в отток.
- **Решение:**
  - оферта с тарифами, правилами возврата и реквизитами;
  - политика конфиденциальности: какие данные, где хранятся (ЕС, Supabase eu-west-1), сколько хранятся;
  - контакты поддержки: WhatsApp или Telegram и часы работы.
  - Опубликовать на сайте и вписать адреса в `billing-config.js`.

### 2.2. Доставка писем для входа (P0, новая находка)
- **Суть:** вход в расширение и админку идёт по коду из письма. Встроенная почта Supabase отправляет **всего несколько писем в час** (`billing/README.md:93`). Своя почта (SMTP) не подтверждена.
- **Чем грозит:** в день запуска уже 5–10 продавцов не получат код. На 1–2 тыс. клиентов вход фактически не работает. Это худший первый опыт: «установил, а войти не могу».
- **Решение:**
  - Supabase → Authentication → Emails → SMTP Settings: подключить Resend, Mailgun или почту домена, прописать SPF и DKIM;
  - поднять лимит отправки (Auth → Rate Limits);
  - проверить, что в шаблоне письма есть `{{ .Token }}`.

### 2.3. Инфраструктура под платящих клиентов (P0 для массового запуска, P1 для беты)
- **Суть:** организация на тарифе **Free**. Бэкап — только самописный через GitHub Actions в артефакты на 30 дней, восстановление ни разу не проверялось. `pg_cron` нет, бот и оповещения зависят от расписания GitHub.
- **Чем грозит:**
  - потеря или повреждение базы означает потерю всех оплат и подписок, а восстановить базу на конкретный момент нельзя;
  - на Free есть лимиты на размер базы, трафик и вызовы функций, и гарантий доступности нет;
  - расписание GitHub не гарантирует время запуска и само отключается в репозитории без активности 60 дней, тогда бот и оповещения тихо перестанут работать.
- **Решение:**
  - перейти на **Pro ($25 в месяц)**: ежедневные бэкапы и при желании PITR;
  - один раз проверить восстановление из бэкапа на тестовом проекте;
  - включить `pg_cron` и `pg_net` и перевести на них запуск бота и `ops_digest`.

### 2.4. Автоматизация оплат (P0 для 1–2 тыс., для беты допустимо вручную)
- **Суть:** каждый счёт подтверждается вручную через `admin_confirm_invoice`. Автоплатежей, вебхуков и сверки нет.
- **Чем грозит:**
  - 35–70 подтверждений в день, 7 дней в неделю;
  - любая задержка: клиент оплатил, а доступа нет, хотя льготный период 3 дня отчасти смягчает это;
  - больше тикетов, потерянные продления и выгорание владельца;
  - автопродления нет, поэтому каждый месяц часть клиентов просто забывает заплатить.
- **Решение (по шагам):**
  1. Уже сейчас: в админке подтверждать несколько счетов сразу и смотреть очередь по времени ожидания. Счета ищутся по телефону или сумме.
  2. Импорт выписки Kaspi в CSV с автоматическим сопоставлением по сумме, телефону и номеру счёта.
  3. Платёжный шлюз с вебхуком (Kaspi через агрегатора, FreedomPay, CloudPayments KZ, ePay Halyk) → Edge Function → повторно безопасное подтверждение счёта. Затем регулярные платежи.

### 2.5. Лазейки в монетизации (P1)
- **Делёж одного аккаунта.** Лимит магазинов сверяется на стороне клиента, со списком магазинов в конкретном браузере (`licenseGate` в `service-worker.js:1387`, `allowedStoreIds`). По тем частям `get_license`, что я смотрел, сервер не сравнивает число заявленных аккаунтом магазинов (`store_claims` по `user_id`) с оплаченным лимитом. Значит, 3 продавца на тарифе «1 магазин» с одним логином на трёх компьютерах будут работать все. **Решение:** в `get_license` считать уникальные магазины аккаунта за последние 30 дней. Если их больше `store_limit`, ставить статус `over_limit` и показывать предложение докупить магазины.
- **Пробный период.** Изменённое расширение может не отправлять ключи магазинов. **Решение:** без хотя бы одного заявленного магазина не выдавать пробный период полностью, давать только демо-режим.
- **Изменённое расширение вообще.** Вся работа с API Kaspi идёт на стороне клиента, поэтому распакованную и исправленную копию полностью не остановить. **Решение:**
  - переносить ценность на сервер: Telegram-сводки, аналитика (insights), командная работа, история;
  - устанавливать только из Chrome Web Store;
  - проверять, что поля лицензии подписаны, в нескольких местах кода.
- **Льготный период без сети (3 дня)** — это нормально. Он ограничен сроком действия подписанного токена (`claims.exp + offlineGraceDays`, `billing.js:352`), бесконечно продлить его нельзя.

### 2.6. Наблюдаемость и поддержка (P1)
- **Суть:**
  - нет сбора ошибок из расширений клиентов: при 2 тыс. установок вы узнаете о проблеме из тикетов, а не из графика;
  - `getStorageHealth()` нигде в интерфейсе не используется (поиск по `background`, `dashboard`, `popup` пуст), поэтому продавец не узнает, что данные перестали сохраняться;
  - тикеты есть (`support_tickets`), но нет готовых ответов и раздела FAQ в расширении.
- **Чем грозит:** тихие сбои у части клиентов, отток без объяснений, поддержка на ручном труде.
- **Решение:**
  - таблица `client_errors` и RPC с ограничением частоты, куда расширение раз в час отправляет обезличенные ошибки, и сводка по ним в `ops_digest`;
  - плашка в дашборде «Хранилище переполнено, очистите…» на основе `getStorageHealth()`;
  - 10–15 готовых ответов в админке и FAQ по частым ошибкам Kaspi: просроченный токен, 429, смена пароля кабинета.

### 2.7. Выпуск обновлений и зависимость от интерфейса Kaspi (P1–P2)
- **Суть:** версия `0.1.0`, процесса публикации в Chrome Web Store, поэтапного выпуска и отката нет. Режим работы в кабинете (`content_scripts` на страницах Kaspi, `manifest.json:41-56`) зависит от вёрстки Kaspi.
- **Чем грозит:** Kaspi поменял страницу — у всех 2 тыс. клиентов одновременно сломалась функция. Проверка в Chrome Web Store занимает от часов до дней, и быстро выпустить исправление нельзя.
- **Решение:**
  - удалённые флаги функций в `billing_config`, например `features.cabinet = false`, которые расширение читает вместе с лицензией: это выключатель за секунды без нового выпуска;
  - баннер через уже существующий `get_service_status`;
  - процесс выпуска: поднять версию, собрать (`build-release.mjs`), показать новую версию сначала части пользователей и опубликовать.

## 3. Что уже сделано на высоком уровне

1. **Работа с API Kaspi.** Глобальный лимит 4 запроса одновременно и 3 на магазин, повторы с учётом Retry-After и 429, автоматический выключатель (circuit breaker) после 3 сбоев на 10 минут, атомарная запись снимков и накладных через `safeSet`. Это правильная основа для 1–2 тыс. магазинов, переделывать её не нужно.
2. **Модель безопасности базы.**
   - RLS включён на всех 21 таблице, вся работа идёт через `SECURITY DEFINER` RPC с проверками ключа, `is_admin()` и `auth.uid()`;
   - фиксированный `search_path`;
   - 12 миграций совпадают с репозиторием, функции, доступные без входа, проверены Opus;
   - пробный период выдаётся один раз на магазин (миграция 012).
3. **Лицензия.** Права пользователя записываются в подписанный токен Supabase (`custom_access_token_hook`, ES256), а расширение проверяет подпись. Без сети лицензия работает ограниченное время. Это защита уровня зрелых SaaS.
4. **Тесты и CI.** 6 unit-наборов и 283 SQL-проверки, включая тесты на атаки. Есть e2e, ночной бэкап и оповещения о сбоях Kaspi (`ops_digest`). Админка работает без сборки и выкладывается за 5 минут.

## 4. План выхода на рынок

**Да, закрытую бету на 20–50 клиентов стоит запускать сейчас**, но только после 4 условий (все делаются руками владельца, 1–2 дня).

**Условия беты (P0):**
1. Подключить свою почту в Supabase и проверить, что письмо с кодом приходит за 1 минуту.
2. Опубликовать оферту (можно бета-оферту с ценой 0 или со скидкой), политику конфиденциальности и контакты поддержки. Вписать их в `shared/billing-config.js`.
3. Telegram-бот: задать секреты и прогнать один реальный цикл на своём чате.
4. Один раз проверить восстановление бэкапа или сразу перейти на Pro ($25).

Подтверждать оплаты вручную на 50 клиентах можно.

**Что измерять в бете (2–4 недели):**
- доля продавцов, которые подключили магазин за первые 10 минут (цель ≥ 70%);
- сколько клиентов пользуются продуктом через 7 дней;
- тикетов на клиента в неделю;
- переход из пробного периода в оплату;
- время от оплаты до подтверждения;
- ошибки Kaspi API на одного клиента.

**Перед масштабированием до 1–2 тыс.:**
- тариф Pro и `pg_cron`;
- автоматизация оплат (хотя бы импорт выписки);
- закрыть делёж аккаунта;
- сбор ошибок из расширений и плашка хранилища;
- удалённые флаги функций;
- нагрузочный прогон `billing/loadtest` на 2 тыс. аккаунтов;
- процесс выпуска в Chrome Web Store;
- CAPTCHA и защита от утёкших паролей (Leaked Password Protection).

**Ориентир:** бета через 1–2 дня, рост до 300–500 клиентов через 3–5 недель после закрытия P1, 1–2 тыс. после автоматизации оплат.
