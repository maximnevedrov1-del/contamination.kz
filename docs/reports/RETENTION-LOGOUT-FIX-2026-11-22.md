## Пункт 3. Счета и согласия больше не удаляются вместе с аккаунтом

**Проблема.** При удалении пользователя база каскадно удаляла его счета и записи о согласии с офертой. Это нарушает обязанность хранить записи об оплатах и лишает доказательства акцепта.

**Что сделано:**
- После удаления пользователя счета и согласия остаются, только без привязки к аккаунту (`ON DELETE SET NULL`). Сумма, телефон, даты, IP и браузер сохраняются.
- Вместо email в них записывается его хэш (`account_ref`, SHA-256): счёт можно найти по старому email, но сам адрес не хранится.
- Новая функция для админа `admin_delete_account(пользователь, email)`:
  - работает только у админа;
  - email нужен как подтверждение (регистр и пробелы не важны);
  - другого админа или себя удалить нельзя;
  - неоплаченные счета перед удалением отменяются;
  - возвращает список прайс-листов клиента. Их файлы нужно удалить вручную через Supabase → Storage: из SQL Supabase удалять файлы не разрешает.
- В списке счетов админки (`admin_invoices`) теперь видны и счета удалённых аккаунтов, их можно найти по старому email.

## Пункт 4. Автоочистка старых данных

**Проблема.** Политика обещает сроки хранения, а обращения в поддержку не удалялись никогда. Остальные данные удалялись только попутно, при вызове отдельных функций.

**Что сделано.** Функция `purge_expired()` удаляет:

| Данные | Срок |
|---|---|
| Отвеченные или закрытые обращения в поддержку | 365 дней после ответа (настраивается: `ops_settings.ticket_keep_days`, 30–3650) |
| Данные Telegram-сводки | 30 дней |
| История Telegram-уведомлений | 120 дней |
| Счётчики API | 14 дней |
| Статистика использования | 400 дней |
| Ссылки привязки Telegram | после истечения |

- Открытые обращения не удаляются.
- Очистка запускается не чаще раза в сутки из `ops_digest`, который каждые 10 минут вызывает уже работающая проверка сбоев. Отдельное расписание не понадобилось.
- Админ может запустить очистку вручную: `admin_purge_expired()`.
- Клиенты вызвать очистку не могут.

## Пункт 6. Продавца больше не выкидывает из аккаунта при сбоях сервера

**Проблема.** При ответах Supabase 5xx или 429 на обновление сессии расширение удаляло сессию, и продавцу приходилось входить заново. Была и вторая ошибка: без сети расширение продолжало использовать уже истёкший токен, получало 401 и тоже выкидывало продавца.

**Что сделано:**
- Выход из аккаунта теперь только если Supabase отказал в обновлении сессии (400/401/403).
- При 5xx, 429 или без сети сессия сохраняется, а лицензия берётся из кэша, как и раньше, до 3 дней (`offlineGraceDays`).
- Истёкший токен больше не отправляется: вместо этого используется кэш.
- Если сервер отклонил запрос лицензии (401), расширение один раз обновляет сессию и повторяет запрос. Выход — только если отказ повторился.
